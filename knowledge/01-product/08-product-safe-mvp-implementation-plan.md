## 1. Executive Verdict

The correct MVP is **not** the Vietnamese long-form ambition plan. The correct MVP is the funded baseline in `07-business-proposal-en.md`:

- 1 route-dense cluster in Hanoi or HCMC
- 12-20 curated merchants
- 300-800 invited VETC users
- 5 productized modules
- 4 human-operated workflows
- 12-week build and launch window

The implementation objective is:

> Prove one repeatable merchant-and-user operating unit where VETC route context creates better timing, better trust, better completion, and better merchant discipline than the offline status quo.

The MVP is product-safe if it does **less** product surface and **more** operational truth:

- Build consumer + merchant flows only where software must exist.
- Keep ops/control tower workflows manual, but data-backed and testable.
- Avoid ML, membership, full Control Tower, automated settlement, national rollout, and broad cross-sell until the repeatable-cluster gate.
- Treat VETC data + identity bridge as a binary stage gate before Week 3.

## 5. Architecture Review

### Accepted Architecture

```
React Native app
  ├─ Consumer route: recommendation -> hold -> check-in -> payment -> evidence -> rating/complaint
  └─ Merchant route: queue -> slot update -> demand alert -> photos -> completion -> summary

FastAPI backend
  ├─ Auth / roles
  ├─ Catalog / SOP rules
  ├─ Booking / hold / check-in
  ├─ Merchant slots / queue
  ├─ Payments / ledger
  ├─ Evidence upload
  ├─ Complaints / refund queue
  ├─ Recommendations
  └─ Ops exports

Workers
  ├─ Intelligence worker: VETC route data, weather, scoring, stale detection
  └─ Notification worker: FCM, in-app notifications, Zalo fallback, outbox sweep

Data / Infra
  ├─ Supabase Postgres + Auth + Realtime
  ├─ Redis Cloud
  ├─ S3-compatible object storage
  ├─ FCM
  └─ External: VETC API, VETC Loyalty, GoongIO, Weather, VETC Wallet
```

### Architecture Rules

- Supabase Auth + Row Level Security must enforce tenant and role boundaries. Supabase docs confirm JWT-backed RLS can use `auth.uid()` and JWT metadata for access rules.
- Use a roles array in JWT claims for multi-role users, matching the existing project learning.
- Backend service-role access must not become an authorization bypass. Each endpoint still checks actor, role, merchant ownership, and booking ownership.
- Slot hold must be a single PostgreSQL transaction. Either atomic `UPDATE ... WHERE available_bays > 0` or row-level locking. PostgreSQL official docs confirm row locks prevent conflicting writers until transaction end.
- Redis pub/sub is fire-and-forget. Keep DB outbox + sweeper for booking completion, notification, payment callback, and complaint events.
- Celery tasks must be retryable and observable. Celery docs warn that unacknowledged tasks can be redelivered after visibility timeout; use retries, backoff, idempotency keys, and a dead letter queue for stuck work. Idempotency means duplicate calls produce one business result, not two bookings or two refunds.
- Supabase pooler config must be explicit. Supabase docs distinguish transaction/session pooler and direct/session connections; app traffic and migrations need separate connection strings.

### Architecture Status

Clear for P0 after seven gates:

1. VETC data contract signed: fields, freshness, auth, latency, fallback semantics.
2. VETC identity bridge signed: user ref, vehicle ref, phone, consent, deep link, session ownership.
3. Legal/compliance approves consent, retention, invoicing, and photo evidence handling.
4. Merchant cohort locked: 12-20 targets, 1 flagship, backup merchants.
5. Service catalog v1 locked: 6 services, duration, price rules, proof requirements.
6. Payment state machine approved: wallet, cash, failure, duplicate callback, refund states.
7. VETC Loyalty contract approved if point redemption ships in P0: profile, tier, quote, reserve, commit, release, reversal, campaign budget, and reconciliation semantics.

### Launch-Blocking Tests

1. Two users hold the same slot at the same time; one succeeds and one gets `SLOT_ALREADY_HELD`.
2. Wallet succeeds, times out, fails after hold, and callback arrives twice.

4. Celery task crashes; task lands in dead letter queue and alert fires.
5. Redis pub/sub message is missed; outbox sweeper still delivers notification.
6. Merchant slot stale >2h; merchant is removed from recommendations.
7. Complaint exceeds 48h; escalation alert goes to ops manager.
8. Vietnamese UI strings render without clipping on 320px Android.
9. VETC identity deep link opens with missing consent and routes user to consent recovery.

## 8. Performance Review

### P0 Targets

| Path | Target | Implementation Rule |
|---|---:|---|
| `GET /api/recommendations` | <1s | batch GoongIO distance matrix, cache stable merchant distances |
| `POST /api/bookings/hold` | <200ms | single PostgreSQL write transaction, no external API calls |
| `POST /api/payments/initiate` | <500ms | async confirmation state, do not block slot state on wallet callback |
| `GET /api/merchants/{id}/slots` | <100ms | Redis read cache, PostgreSQL write source of truth |
| Photo presigned URL | <100ms | client compresses to <500KB, upload retries offline |

### Performance Findings

- P0 traffic is small, but push windows can create bursts. Batch work by cohort, not one expensive API call per user.
- Celery Beat per-user tasks are acceptable at 300-800 users. Revisit before 100K users.
- Photo upload is the main mobile latency risk. Compress client-side and persist local upload queue.
- Supabase connection pool is unlikely to bottleneck P0, but pooler configuration must be done before live pilot.
- Manual ops exports become the first real bottleneck if owners and cadence are unclear.

Performance status: **clear for P0**, re-review before P1.

## 15. Worktree Parallelization

Schema first. Everything else depends on it.

| Step | Modules touched | Depends on |
|---|---|---|
| A. Schema + migrations | backend shared models, SQL | none |
| B. Auth + roles + RLS | backend auth, Supabase policies | A |
| C. Catalog + SOP seeds | backend shared, SQL seeds | A |
| D. Booking + check-in | backend API | A, B, C |
| E. Merchant queue + slots | backend API, mobile merchant | A, B, C |
| F. Payment ledger | backend API, wallet integration | A, B, D |
| G. Evidence upload | backend API, mobile camera | A, B, D, E |
| H. Recommendations + scoring | shared scoring, API, worker | A, B, C |
| I. Notifications + outbox | worker, Redis, FCM/Zalo | A, H |
| J. Complaints + ops exports | backend API, ops SQL | A, B, D, F, G |
| K. Consumer mobile | mobile consumer | D, F, G, H |
| L. Merchant mobile | mobile merchant | E, G |
| M. Ops runbooks/tabletop | ops docs, SQL exports | J |

Parallel lanes:

```
Phase 1: A -> B -> C

Phase 2 parallel:
  Lane 1 Core Transaction: D -> F -> J
  Lane 2 Merchant/Evidence: E -> G
  Lane 3 Intelligence/Notify: H -> I

Phase 3 parallel:
  Lane 4 Consumer Mobile: K
  Lane 5 Merchant Mobile: L
  Lane 6 Ops Workflow: M
```

Conflict flags:

- Lanes 1 and 2 both touch shared booking/evidence models. Keep model ownership in Lane 1 until migrations stabilize.
- Lane 3 imports scoring and notification event contracts. Do not let it change booking state definitions independently.
- Mobile lanes should consume OpenAPI-generated clients or a frozen API contract, not hand-rolled endpoint strings.
